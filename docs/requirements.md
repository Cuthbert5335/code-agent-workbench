# CodeXXX 完整项目需求文档

文档版本：v1.1  
文档状态：项目总需求基线  
项目名称：CodeXXX  
项目类型：开源、本地优先、可自部署的代码分析与开发 Agent 网页应用

## 1. 文档说明

本文件描述 CodeXXX 的完整产品目标和长期功能范围，不等同于“第一版最小可运行版本”。后续开发可以分阶段交付，但每个阶段都应回到本文件检查产品方向，避免项目逐渐变成没有边界的聊天机器人。

本文档同时作为：

- 产品需求文档。
- Agent 行为约束说明。
- 系统功能范围说明。
- 安全和权限设计依据。
- 测试与验收依据。
- 后续拆分开发任务的总蓝图。

## 2. 项目背景

开发者在学习或维护代码项目时，经常需要反复完成以下工作：

- 理解陌生项目的目录结构。
- 查找某个函数、类或接口的调用关系。
- 分析错误日志和异常堆栈。
- 编写、修改和解释代码。
- 补充测试。
- 阅读文档、配置和依赖信息。
- 在修改后运行检查并确认没有引入明显问题。

普通聊天机器人无法稳定获取项目上下文，也不能可靠地完成“分析、修改、验证”的连续流程。CodeXXX 的目标是把大语言模型放入一个受控的代码工作区中，使它能够在用户确认的边界内理解项目、提出计划、生成修改、运行验证并汇报结果。

## 3. 产品定位

CodeXXX 是一个以代码仓库为工作对象的开源、本地优先智能开发 Agent。它通过网页提供交互界面，通过后端管理项目文件、代码索引、模型调用、工具调用、补丁审核和验证任务，并允许开发者在自己的电脑上阅读源码、运行测试和排查 Agent 行为。

产品默认面向本地自部署和学习使用，而不是要求所有用户接入统一的在线 SaaS。服务模式、组织协作和在线部署属于可选扩展；本地代码、SQLite 数据和模型密钥默认保留在用户自己的运行环境中。

CodeXXX 的核心工作循环是：

```text
理解任务
  -> 检查项目上下文
  -> 制定执行计划
  -> 检索相关代码
  -> 调用受控工具
  -> 生成或应用补丁
  -> 运行检查和测试
  -> 汇报修改结果与遗留问题
```

CodeXXX 不是完全自主、无限权限的程序。用户始终拥有项目文件和高风险操作的最终确认权。

## 4. 产品目标

### 4.1 用户目标

CodeXXX 应帮助用户：

- 更快理解代码项目。
- 通过自然语言定位代码问题。
- 获得有依据的修改建议。
- 在确认后生成可审阅的代码补丁。
- 在修改后自动运行合适的检查。
- 保留任务过程、修改内容和验证结果。

### 4.2 学习目标

项目本身应成为 Agent 工程学习项目，使开发者能够理解：

- 前后端分离。
- 模型上下文构建。
- RAG 和代码检索。
- Tool Calling。
- Agent 状态机和工作流。
- 代码补丁和 Diff。
- 沙箱执行。
- 评测、日志和可观测性。
- 权限控制与数据隔离。

### 4.3 工程展示目标

项目应能够作为求职作品展示：

- 产品需求和架构设计能力。
- 全栈开发能力。
- LLM 和 Agent 集成能力。
- 可靠性与安全意识。
- 测试、评测和部署能力。

## 5. 目标用户

### 5.1 初学者

需要解释项目结构、语法、函数作用和错误原因的学习者。

### 5.2 个人开发者

需要快速定位 Bug、生成测试、整理重构方案的开发者。

### 5.3 团队开发者

需要在团队代码库中查询规范、分析模块关系和辅助处理任务的开发者。

### 5.4 项目维护者

需要查看 Agent 执行轨迹、审阅补丁、追踪失败任务和管理项目权限的人员。

## 6. 典型用户故事

### US-01 理解项目

作为一个刚接手项目的开发者，我希望让 CodeXXX 概括目录结构、启动流程和主要模块，以便快速建立整体认识。

### US-02 定位问题

作为一个遇到报错的开发者，我希望粘贴错误日志或选择相关文件，让 CodeXXX 分析可能原因并指出依据。

### US-03 生成修改方案

作为一个开发者，我希望 CodeXXX 先给出修改计划，再生成可查看的 Diff，而不是直接改动我的文件。

### US-04 审阅并应用补丁

作为一个开发者，我希望逐文件查看修改内容，在确认后应用补丁，并且可以撤销或恢复到修改前状态。

### US-05 自动验证

作为一个开发者，我希望 CodeXXX 在应用修改后运行格式检查、类型检查和测试，并告诉我哪些通过、哪些失败。

### US-06 学习代码

作为编程初学者，我希望回答同时包含结论、代码依据和必要的基础解释，并可以继续追问。

### US-07 管理项目

作为项目维护者，我希望不同用户只能访问自己有权限的代码项目，并能够删除项目数据和历史任务。

## 7. 产品范围

### 7.1 产品范围内

- 本地代码项目和远程代码项目的导入。
- 文件浏览、代码搜索和符号检索。
- 面向代码的对话。
- 任务计划和 Agent 执行轨迹。
- 受控工具调用。
- 修改建议、Diff 审阅和用户确认。
- 测试、构建和静态检查。
- 会话、项目和任务历史。
- 模型配置和用量统计。
- 用户、权限和数据隔离。
- 本地部署、自部署文档和可重复运行。
- 面向 Agent 学习的基础评测和可观测性。
- 可选的组织协作能力。

### 7.2 产品范围外

- 代替开发者做最终代码审查。
- 保证模型回答绝对正确。
- 无限制执行任意代码和命令。
- 自动访问用户未授权的文件、网络服务或凭据。
- 在没有人工确认的情况下执行破坏性操作。
- 第一阶段支持所有编程语言的完整语义理解。

## 8. 产品形态与运行模式

CodeXXX 支持两种运行模式。

### 8.1 本地模式

适合个人学习和隐私敏感项目：

- 前端和后端运行在用户电脑上。
- 代码默认不离开本机，只有选中的上下文发送给模型服务。
- 模型 API Key 由本地后端保存。
- 用户通过 `localhost` 访问网页。

### 8.2 服务模式（可选扩展）

适合局域网或后续在线团队协作，不是当前开源自部署主线：

- 前端、后端和数据库部署在服务器。
- 用户通过域名和 HTTPS 访问。
- 项目、会话和任务数据按用户和组织隔离。
- 高风险工具运行在隔离沙箱中。
- 支持管理员管理模型、用户和用量限制。

## 9. 系统角色与权限

### 9.1 普通用户

- 创建和访问自己拥有的项目。
- 上传或导入代码。
- 发起分析任务。
- 查看和确认自己的 Diff。
- 查看自己的会话和任务历史。

### 9.2 项目协作者

- 访问被授予权限的项目。
- 发起分析和修改任务。
- 查看项目任务和执行日志。
- 是否可以应用补丁由项目权限决定。

### 9.3 项目管理员

- 管理项目成员和权限。
- 管理项目设置和模型策略。
- 删除项目及其数据。
- 查看项目用量和失败任务。

### 9.4 系统管理员

- 管理用户、组织和全局配置。
- 管理模型服务、额度和限流策略。
- 查看系统健康状况和审计记录。
- 不应默认查看用户代码正文，除非具备明确的审计授权。

## 10. 功能需求

### FR-01 用户注册与登录

服务模式支持用户注册、登录、退出和密码重置。可以后续接入 OAuth，但第一阶段至少要支持安全的账号密码或已有身份认证服务。

要求：

- 密码不得明文保存。
- 登录失败应有限流。
- 会话令牌应有过期时间。
- 退出后令牌失效。

### FR-02 项目管理

用户可以创建、重命名、归档和删除项目。

项目字段至少包括：

- 项目名称。
- 项目描述。
- 所有者。
- 创建时间和更新时间。
- 运行模式。
- 默认模型配置。
- 文件数量和索引状态。

删除项目属于高风险操作，需要二次确认，并明确说明不可恢复的数据范围。

### FR-03 项目导入

支持以下导入方式：

- 选择本地文件。
- 选择多个本地文件。
- 选择本地项目目录。
- 上传压缩包。
- 从 Git 仓库地址导入。
- 后续支持 GitHub、GitLab 等授权连接。

导入时必须：

- 忽略 `.git`、`node_modules`、`dist`、`build`、缓存和密钥文件。
- 识别文件语言和编码。
- 限制单文件、单项目和总存储大小。
- 提供导入进度和失败原因。
- 不执行项目中的安装脚本或构建脚本。

### FR-04 文件浏览器

用户可以按目录树查看已导入项目。

支持：

- 展开和收起目录。
- 查看文件内容。
- 搜索文件名。
- 查看文件大小和语言类型。
- 标记索引状态。
- 查看文件是否被某次回答引用。

### FR-05 代码搜索

系统提供至少三种搜索能力：

- 文件名搜索。
- 文本关键词搜索。
- 符号或函数名搜索。

搜索结果应包含文件路径、行号、匹配片段和上下文。

后续可使用 Tree-sitter 等语法解析器增强类、函数、接口和引用关系检索。

### FR-06 代码索引与检索

系统应建立项目索引，用于在问题提交时选取相关上下文。

索引分为三个层次：

1. 文件元数据索引：路径、语言、大小、更新时间。
2. 文本块索引：按代码结构切分的代码片段。
3. 语义索引：可选的向量嵌入和向量检索。

索引过程必须显示状态：未开始、处理中、已完成、部分失败、失败。用户应能够重新索引。

### FR-07 对话与问题输入

用户可以在项目上下文中发起对话。

问题输入支持：

- 普通文本。
- 选中代码后提问。
- 附加错误日志。
- 指定文件或目录。
- 指定任务类型，例如解释、排错、重构、测试和文档。

系统应保留当前会话的消息、引用、工具调用和最终结果。

### FR-08 上下文构建

后端根据问题、对话历史、用户选中的文件和检索结果构建模型上下文。

上下文构建应包括：

- 项目基本信息。
- 用户问题。
- 相关代码片段。
- 文件路径和行号。
- 必要的配置和文档片段。
- 安全规则和工具权限。

上下文必须设置 token 或字符上限。超过上限时，系统应优先保留与问题相关的片段，并提示发生了截断或摘要。

### FR-09 Agent 任务规划

对于需要多步处理的问题，Agent 应先生成可读的任务计划，例如：

```text
1. 检查相关模块和调用位置。
2. 找出异常的产生路径。
3. 提出修改方案。
4. 生成补丁。
5. 运行测试并汇报结果。
```

用户可以查看计划，并在执行前取消任务。高风险任务必须等待用户确认。

### FR-10 工具调用

Agent 可以使用受控工具完成工作。工具至少包括：

- 读取文件。
- 列出目录。
- 搜索文本。
- 搜索符号。
- 查看 Git Diff。
- 创建补丁草稿。
- 运行允许的静态检查。
- 运行允许的测试命令。
- 生成项目摘要。

每个工具必须有：

- 明确的输入参数。
- 参数校验。
- 权限要求。
- 超时限制。
- 输出大小限制。
- 错误返回格式。
- 审计记录。

模型不得通过自然语言绕过工具权限。

### FR-11 计划模式与执行模式

系统提供至少两种模式：

- 计划模式：只分析和提出方案，不修改文件、不运行命令。
- 执行模式：在权限和用户确认范围内调用工具。

默认进入计划模式。用户明确确认后，才进入执行模式。

### FR-12 代码修改建议

Agent 不直接把生成文本写入文件，而是生成结构化补丁。

补丁必须包含：

- 修改的文件。
- 修改前后的 Diff。
- 修改原因。
- 可能的风险。
- 建议运行的验证命令。

用户可以逐个文件查看、接受、拒绝或取消补丁。

### FR-13 补丁应用与撤销

用户确认后，系统才可以应用补丁。

要求：

- 应用前检查文件版本是否发生变化。
- 发生冲突时停止并提示用户。
- 应用前保存可恢复状态。
- 支持撤销最近一次应用。
- 记录应用人、时间、文件和补丁摘要。

### FR-14 验证与测试

补丁应用后，Agent 可以根据项目配置建议并运行：

- 单元测试。
- 类型检查。
- 静态检查。
- 格式检查。
- 构建命令。

命令必须来自允许列表或由用户明确确认。系统不得自动运行未知的安装、删除、网络上传或系统管理命令。

验证结果应显示：

- 命令名称。
- 开始和结束时间。
- 退出码。
- 标准输出和错误输出摘要。
- 通过、失败、超时或跳过状态。

### FR-15 代码执行沙箱

当产品后续支持运行用户代码时，必须使用隔离环境。

沙箱至少需要：

- 独立容器或虚拟环境。
- CPU、内存和执行时间限制。
- 网络默认关闭。
- 只读基础镜像。
- 临时文件系统。
- 进程和系统调用限制。
- 任务完成后清理环境。

未完成沙箱前，产品不得提供任意代码执行功能。

### FR-16 回答展示

回答页面应展示：

- 最终回答。
- 任务计划。
- 引用文件和行号。
- 工具调用摘要。
- 修改 Diff。
- 测试和验证结果。
- 警告、不确定性和失败原因。

回答应支持 Markdown、代码块和基本语法高亮。

### FR-17 历史记录

用户可以查看：

- 项目列表。
- 会话列表。
- 任务状态。
- 任务输入和最终回答。
- 已应用补丁。
- 验证结果。

用户可以删除会话。删除策略应在界面上明确说明是否同时删除代码上下文、索引和日志。

### FR-18 模型配置

用户或管理员可以配置：

- 模型服务商。
- Base URL。
- 模型名称。
- 温度或等效生成参数。
- 最大输出长度。
- 超时时间。
- 每日或每月用量限制。

密钥输入框应避免在页面中回显完整密钥。服务端日志不得记录密钥。

### FR-19 评测系统

系统应支持建立代码问题评测集，每条样本至少包括：

- 项目快照。
- 用户问题。
- 期望引用文件。
- 期望回答要点。
- 是否允许修改。
- 期望测试结果。

核心指标包括：

- 问题理解正确率。
- 引用文件准确率。
- 工具调用成功率。
- 补丁应用成功率。
- 测试通过率。
- 平均响应时间。
- 平均模型成本。
- 用户取消率和失败率。

### FR-20 管理和监控

管理员需要看到：

- 服务健康状态。
- 模型调用次数和耗时。
- 失败请求数量。
- 工具调用失败情况。
- 存储使用量。
- 用户或组织用量。

日志应支持按请求 ID、用户、项目和任务查询，但必须遵守隐私和最小化原则。

## 11. Agent 状态与任务生命周期

每个 Agent 任务至少包含以下状态：

```text
created
  -> planning
  -> waiting_for_confirmation
  -> executing
  -> reviewing
  -> validating
  -> completed
```

异常状态包括：

```text
cancelled
failed
timed_out
blocked
```

状态转换必须可追踪。任务不能在没有记录的情况下从计划直接跳到文件修改完成。

## 12. 数据模型

长期版本至少需要以下实体：

- User：用户。
- Organization：组织或团队。
- Project：代码项目。
- ProjectMember：项目成员和权限。
- File：项目文件元数据。
- FileChunk：代码切片。
- Symbol：函数、类、接口等符号。
- IndexJob：索引任务。
- Conversation：会话。
- Message：消息。
- AgentTask：Agent 任务。
- ToolCall：工具调用。
- Patch：代码补丁。
- ValidationRun：验证运行记录。
- ModelConfig：模型配置。
- UsageRecord：用量记录。
- AuditLog：审计日志。

本地学习阶段可以先使用内存数据或 SQLite，但数据模型应尽量沿用以上概念，便于后续升级到 PostgreSQL。

第一阶段只需实现健康检查、项目分析和必要的文件上传接口，不要求一次实现全部 API。

## 14. 安全需求

### 14.1 文件安全

- 只读取用户明确选择或上传的文件。
- 默认拒绝密钥、凭据和系统敏感目录。
- 限制文件类型、大小、数量和总上下文长度。
- 对路径进行规范化，防止路径穿越。
- 不信任用户提交的文件名和项目配置。

### 14.2 模型安全

- API Key 只保存在后端。
- 不把系统提示词、内部配置和凭据暴露给模型或用户。
- 对工具调用参数进行服务端校验。
- 不能因为用户在代码或文档中写了指令，就改变系统安全策略。
- 对模型输出进行结构化解析和字段校验。

### 14.3 命令安全

- 第一版禁止执行用户代码。
- 后续只允许执行配置过的命令。
- 高风险命令必须人工确认。
- 默认关闭网络访问。
- 所有命令记录执行人、目录、参数、耗时和退出码。

### 14.4 多用户安全

- 项目所有者和成员权限必须在后端检查。
- 不能仅依赖前端隐藏按钮来实现权限控制。
- 用户只能读取自己有权限的项目和任务。
- 日志、索引和缓存必须实现用户或项目隔离。

## 15. 非功能需求

### 15.1 可用性

- 新用户可以按照 README 启动项目。
- 页面必须有清晰的空状态、加载状态、错误状态和成功状态。

### 15.2 性能

- 普通健康检查应快速返回。
- 文件导入和索引应支持进度显示。
- 长任务不能阻塞整个 Web 服务。
- 大模型请求应有超时和取消机制。
- 前端应支持流式显示回答，作为后续增强功能。

### 15.3 可扩展性

- 模型服务商通过适配层切换。
- 工具通过统一注册机制扩展。
- Agent 状态和工具调用与网页展示解耦。
- 文件索引与对话服务解耦。
- 本地存储和服务端数据库之间保留迁移空间。

### 15.4 可观测性

- 每个请求有 request ID。
- 每个 Agent 任务有 task ID。
- 记录阶段耗时、模型耗时、工具耗时和错误。
- 记录 token、费用或等效用量。
- 不记录明文 API Key。
- 对用户代码日志进行脱敏或最小化保存。

### 15.5 可恢复性

- 补丁应用前保留恢复点。
- 任务失败后保留失败原因和已完成步骤。
- 索引失败可以重试。
- 网络错误和模型限流可以有限次数重试。

## 22. 关键决策记录

### 决策 1：网页优先

CodeXXX 最终形态采用网页界面，而不是只做终端工具。原因是网页更容易展示文件树、对话、Diff、任务轨迹和测试结果。

### 决策 2：先单 Agent，再多 Agent

先把一个 Agent 的上下文、工具、权限、状态和验证流程做好，再考虑多 Agent。项目价值不以 Agent 数量衡量。

### 决策 3：先补丁，后直接修改

所有修改先生成 Diff，用户确认后才应用。这是更容易理解和审阅的工程流程。

### 决策 4：先本地，后在线

先在本地完成完整闭环，再增加认证、数据库、沙箱和在线部署，降低学习和排错复杂度。

### 决策 5：先直接检索，后向量 RAG

项目规模较小时，文件筛选、关键词搜索和代码切片足够支撑学习。等基本链路稳定后再引入向量数据库，避免把 Agent 的核心逻辑掩盖在框架中。
